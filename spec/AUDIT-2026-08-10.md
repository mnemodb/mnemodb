## Findings

### #1 HIGH — fence-blind entry splitting (fixed in 0.1.1)
An entry body containing a fenced code block whose contents include `## ` lines (e.g. an agent storing a markdown/code sample) was split at the fence contents — phantom entries with whatever ids/metadata the sample contained. For a memory system for *coding* agents, bodies with code samples are a primary case. **Fix:** the block scanner now tracks ``` / ~~~ fence state; fence interiors are never headings. Regression test added.

### #2 HIGH — lost updates under concurrent writers (fixed in 0.1.1)
Ten parallel `remember()` processes: only 1 of 10 writes survived. Each writer read the same base file and the last atomic rename won. Single-agent MCP usage is sequential (unaffected), but multi-agent and scripted usage is a core scenario. **Fix:** a cross-process writer lock (`withStoreLock`, atomic `mkdir`, 10 s stale-breaking, 5 s timeout) now serializes `remember`, engine `compact(write)`, and CLI `compact --write`. Re-test: 10 of 10 survive. Lock + stale-recovery + concurrency regression tests added.

### #3 MEDIUM — TOCTOU crash in store walk (fixed in 0.1.1)
`loadStore` could crash if a file/dir vanished between `readdir` and `stat` (observed with the lock dir itself). Walk now skips all dot-entries and tolerates vanished paths.

### #4 LOW — open, tracked for v0.2
- `loadStore` ignores root `*.mem.md` files when `.memory/` exists, so a `migrate`d file next to a store is silently unloaded. Recommend: load both, or have `migrate` offer to place output into `.memory/`.
- `list` marks malformed entries with the same `x` as superseded/expired; legend should distinguish damage.
- In-flight MCP requests fired without awaiting responses can interleave reads with a pending write (real clients await; engine-side lock now bounds the damage to reads of the pre-write state).
- `npm warn publish` repository.url normalization — fixed in 0.1.1 manifests.

## Release verdict

0.1.0 should be superseded promptly: both HIGH findings are silent-data-wrongness bugs, the worst class for a memory product. **0.1.1 (this commit) is the recommended first version to advertise.** Suite: 33 tests, 4 consecutive clean runs, including the new fence, lock, stale-lock, and 6-process concurrency tests.

## Addendum — targeted follow-up (same day): i18n + security review

Prompted by four direct questions (Hebrew? emoji? MCP checked? full security audit?). Findings below; all HIGH items fixed in 0.1.1.

### #5 HIGH — non-ASCII content was unsearchable (fixed)
Hebrew, Cyrillic, Arabic, CJK etc. stored and round-tripped fine but `recall` returned **zero** hits for any non-English query: the tokenizer split on `[^a-z0-9]+`, discarding all non-ASCII. For a memory product this is "save but never find." **Fix:** Unicode-aware tokenizer (`[^\p{L}\p{N}]+/u`). Space-delimited scripts (Hebrew, Cyrillic, Arabic, Greek…) now search at the word level. **Known v0.2 limits (documented, not bugs):** CJK needs word-segmentation (no spaces → whole-run matching only); Hebrew/Arabic bound prefixes (בממשק ≠ ממשק) limit phrase matching, same class as English stemming. Emoji round-trip but are not indexed (by design).

### #6 HIGH (security) — recall stripped provenance, defeating the injection defense (fixed)
Spec §10's prompt-injection mitigation requires the consuming agent to know each memory's `src` (user > agent > tool) and treat tool-sourced entries as data, never instructions. But `memory_recall` returned no `src` at all — a memory poisoned via tool output (e.g. injection scraped from a web page) was indistinguishable from a user assertion. **Fix:** `RecallHit` now carries `src` and a computed `untrusted` boolean; `bootContext` tags tool-sourced pins `· untrusted:tool`; the `memory_recall` tool description instructs agents not to obey untrusted content. Regression tests added.
